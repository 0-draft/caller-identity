# 検証

[ノートに戻る](README.ja.md)

このリポジトリの主張をどう検証したか、そして何がまだ仮定のままか。これを書き出す理由は、「検証済み」
には幅があり、その幅が重要だから。

## 確度のはしご

全部が同じ強度ではないので、どの段にいるかを明示する。

| 段 | 根拠 | 適用先 |
| --- | --- | --- |
| 最強 | AWS が期待値付きの計算例を公開しており、それを再現できる | SigV4 ヘッダ認証、presigned URL |
| 強 | AWS がリファレンスで規則を明記しており、挙動がそこから導ける | キー本数、有効期間、condition の意味論 |
| 中 | 公開された擬似コードの独立実装2つが一致する | SigV4a の鍵導出 |
| 弱 | 仕組みからの推論のみ。ベンダーの言明なし | session token の内部的な扱い |

最下段のものはサイトの文言でも「事実」ではなく「仕組み」として書いている。たとえば session token は
「AWS が復号する」ではなく「AWS がセッションの secret に解決する」と書く。AWS がフォーマットを公開
していないため。

## 完全に再現するもの

AWS 公開の計算例2件を、CI で1バイト単位で照合している。

**Glacier の Create Vault**。リクエスト署名のリファレンスから。公開されたキー、secret、タイムスタンプ、
ヘッダに対して、ページが canonical request、string to sign、署名を明記している。3つとも一致する。

**S3 presigned の `test.txt`**。クエリパラメータ認証のリファレンスから。ページ自身が「テストケースと
して使える」と明言している。canonical request、そのハッシュ、署名、完成した URL の全てが一致する。

どちらかが壊れればサイトが表示する署名は全部嘘になるので、両方とも独立した CI ジョブで走らせている。

## AWS ドキュメントの誤り

Glacier の署名ページには2つ目の例、streaming の `Upload Archive` がある。そこに載っている署名値が、
同じページが印字している canonical request から再現できない。

```text
ページの canonical request  →  完全に再現する
ページ記載の署名値:          b092397439375d59119072764a1e9a144677c43d9906fd98a5742c57a2855de6
この実装:                    e8ba379a747bc294584102fd2430f7a563696740882e149c87b15754e7c10a89
独立した Python 実装:        e8ba379a747bc294584102fd2430f7a563696740882e149c87b15754e7c10a89
```

分かりやすい説明の否定もしておく。ページのリクエスト構文には `x-amz-archive-description` と
`x-amz-sha256-tree-hash` が現れるが、canonical request には現れない。この2つを足すと3つ目の値
`9ba94dab5c...` になるので、それも説明にならない。

ちなみに同ページのペイロードハッシュは正しい。`sha256("Welcome to Amazon Glacier.")` は記載通り
`726e392cb4d09924dbad1cc0ba3b00c3643d03d14cb4b823e2f041cff612a628` になる。最終的な署名値だけが
繋がらない。

そこでテストは、canonical request をドキュメントに対して、署名値を相互検算に対して検証し、どちらが
どちらかをコメントに残す形にした。落ちるケースを黙って消すのは簡単で、間違った選択だった。

## 根拠が弱い箇所

**SigV4a の鍵導出。** AWS は導出を擬似コードとしては公開しているが、期待される鍵を示した計算例は
公開していない。つまりベンダーのベクタが存在しない。導出した鍵は、TypeScript ではなくドキュメントから
書き起こした別の Python 実装と突き合わせている。同じ文章の実装2つが一致することは書き写しミスを
排除するが、両方が同じ読み違いをした可能性は排除しない。

**SigV4a の署名。** 原理的に固定できない。ECDSA は乱数を使う。代わりに、署名が導出した公開鍵で検証
できることを assert している。これは AWS が実際に行う検証と同じ。(この実装は `@noble/curves` の既定に
より RFC 6979 で決定的になるが、AWS 側はそうではない。)

## レビューで見つかった誤り

ドキュメントに当て直した結果、既に書いてあった内容から6件の誤りが出た。個別の修正より、パターンの方が
役に立つので列挙する。

1. `CreateAccessKey` のレスポンスに `CreateDate` が抜けていた。
2. 「1ユーザーにつきアクティブキー2本」は誤り。上限は Active / Inactive を問わず同時2本。
3. `AssumeRole` の有効期間で、`DurationSeconds` (900秒以上) と `MaxSessionDuration` の設定値
   (1〜12時間) を混同し、role chaining の1時間上限も抜けていた。
4. session token を「復号される」と書いていた。AWS はフォーマットを公開していない。
5. 時刻ずれを15分と書いていた。それは S3 の値で、AWS の一般的な案内は5分。
6. GitHub のトークン URL は既にクエリ文字列を持つので、audience は `?` ではなく `&` で足す。

どれも書いた時点ではもっともらしく、推測で書いたものは1つも無く、6件とも間違っていた。

## テストが捕まえた2つの思い込み

ドキュメントの問題ではないので、別に記録しておく。

改ざんテストが、string to sign の中の region set を書き換えていた。しかしそこに region set は現れない。
region set が署名に届くのは canonical request のハッシュ経由だけなので、書き換えは何も変えず、署名は
通り続けた。間違っていたのはコードではなくテスト。

もう1つは「2回署名すればバイト列が変わる」という assert。ECDSA は乱数を使うから、という理屈だった。
`@noble/curves` は RFC 6979 の決定的 nonce が既定なので、変わらない。
